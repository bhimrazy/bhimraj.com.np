Most people learn GitHub sideways. You clone a repo for a tutorial, click **Merge** because someone asked you to, copy a workflow file from a blog post, and a few years later you run a team on top of habits nobody ever explained. This series is the explanation: how a small, modern team actually works on GitHub in 2026, from the first commit to protected branches, releases, CI and AI agents that open pull requests.

It's written for five kinds of reader:

- **Founders and non-engineers** who use GitHub daily but never learned what's underneath.
- **New developers** in their first job on a team.
- **Team leads** setting up an org, CI and releases.
- **Experienced engineers** who want the current picture: rulesets, OIDC, immutable releases, agents.
- **Workshop facilitators.** Each part is one 60–90 minute session with exercises built in.

<Callout type="founder" title="The whole series in five lines">
- **Git** keeps the history of your code on every laptop. **GitHub** is the shared copy plus reviews, permissions and automation around it.
- Work happens on short-lived **branches** and lands through reviewed **pull requests**. Small and often beats big and rare.
- Put company code in an **organization**, give access through **teams**, and **protect `main`**. On private repos, protection needs the paid Team plan.
- **GitHub Actions** runs your tests, deploys and chores automatically. The main risk is giving it more access than it needs.
- **AI agents** now open pull requests too. They go through the same reviews and checks as people, and a human still decides what merges.
</Callout>

### Setup notes for facilitators

- **Make a sandbox org with public repos** (`web` and `api` match the examples). On the Free plan, rulesets, required reviews and CODEOWNERS only apply to public repos, so exercises like "protect `main`" quietly do nothing on a private one. Draft PRs on private repos are also plan-dependent at the time of writing, so if a `--private` practice repo refuses a draft PR, recreate it as public. Need private? Put the org on Team and check [Part 3's plan table](/blog/github-organizations-and-teams#plan-reality-free-vs-team-vs-enterprise) first.
- **Accounts.** Every attendee needs their own GitHub account with 2FA on, since the org should require it ([Part 3](/blog/github-organizations-and-teams)). Invite them as members before the day. Sessions 3 and 5 work best in pairs.
- **Install Git and `gh` before Session 1**, which uses `gh` before Part 2 explains it. Send [Part 2's install and sign-in steps](/blog/git-setup-across-devices) as pre-work, and start by having everyone run `gh auth status`.
- **Put a facilitator account on the rulesets' bypass list** so you can unstick a broken exercise without disabling the rule for everyone.
- **Reset between cohorts** by running Session 3's offboarding drill on everyone. It doubles as a demo.

## Glossary

Plain-English definitions for the words the series uses most.

- **Repository (repo):** a project folder plus its full history. On GitHub it also holds the issues, pull requests and settings.
- **Commit:** a saved snapshot of the project with a message saying why it changed.
- **Remote:** the shared copy of a repo that everyone pushes to and pulls from, usually on GitHub. Its default name is `origin`.
- **Branch:** a private line of work. You make changes there without touching the real project until they're reviewed.
- **Pull request (PR):** a proposal to merge a branch into `main`, with a place for review, discussion and automated checks.
- **Draft PR:** a pull request marked "work in progress": visible and running checks, but not ready to merge.
- **Merge:** bringing a branch's changes into another branch. **Squash and merge** turns a whole PR into one commit.
- **Rebase:** replaying your commits on top of newer work, so the history reads as one straight line instead of a fork and a join.
- **Issue:** a tracked piece of work: a bug, a feature or a question.
- **Organization (org):** a shared GitHub account that belongs to a company rather than to one person.
- **Team:** a group of people in an org. You give the team access to repos, then add or remove people from the team.
- **Outside collaborator:** someone who isn't in the org but has access to specific repos, like a contractor.
- **Ruleset:** a set of rules for a branch, such as "changes to `main` need a reviewed PR and passing tests".
- **CODEOWNERS:** a file listing who owns which parts of the code. GitHub asks those people to review changes there.
- **Workflow:** an automation file in GitHub Actions that says what to run and when.
- **Runner:** the machine a workflow's job runs on, hosted by GitHub or by you.
- **Artifact:** a file a workflow produces and keeps, like a build or a test report.
- **Tag and release:** a tag is a permanent name for one commit (`v1.4.2`); a release is a tag plus notes and downloadable files.
- **Agent:** an AI tool (Claude, Codex, Copilot) that works on an issue in its own environment and opens a pull request for a human to review.
